# TR603: undefined stored in an optional property

| | |
|---|---|
| Status | Open in TypeScript 6.0.3 |
| Checked by | `exactOptionalPropertyTypes` in `typerail/tsconfig.json` |
| Priority | P3: latent risk |

## Example

TypeScript accepts this code when `exactOptionalPropertyTypes` is off:

```ts
interface Options {
  timeout?: number;
}

const defaults = { timeout: 1000 };

function settings(overrides: Options): { timeout: number } {
  return { ...defaults, ...overrides };
}

export function proof(): string {
  return settings({ timeout: undefined }).timeout.toFixed();
}
```

At runtime: `TypeError: Cannot read properties of undefined (reading 'toFixed')`

The example is [`test/gaps/TR603.ts`](../../test/gaps/TR603.ts). The test suite checks that TypeScript still accepts it and that it still fails when run.

## Why TypeScript allows it

Without `exactOptionalPropertyTypes`, an optional property `timeout?: number` accepts an explicit `undefined`. TypeScript types an object spread as if optional properties were either absent or present with their declared type, so `{ ...defaults, ...overrides }` is typed `{ timeout: number }` although `overrides.timeout` can overwrite the default with `undefined`.

## How typerail detects it

`typerail/tsconfig.json` enables `exactOptionalPropertyTypes`, which rejects `{ timeout: undefined }` for `timeout?: number`. `typerail report` lists a project that turns it off.

## How to fix it

Enable the flag, and leave optional properties out instead of setting them to `undefined`. Write `timeout?: number | undefined` where an explicit `undefined` is intended.
