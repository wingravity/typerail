# TR207: Overload signature

| | |
|---|---|
| Status | Open in TypeScript 6.0.3 |
| Checked by | `typerail/no-overload-signature` |
| Priority | P1: silent wrong result |

## Example

TypeScript accepts this code under `@wingravity/typerail/tsconfig.json`:

```ts
function parse(text: string): number;
function parse(text: string): number | string {
  return text.trim();
}

export function proof(): string {
  return parse("42").toFixed();
}
```

At runtime: `TypeError: parse(...).toFixed is not a function`

The example is [`test/gaps/TR207.ts`](../../test/gaps/TR207.ts). The test suite checks that TypeScript still accepts it and that it still fails when run.

## Why TypeScript allows it

Overload signatures are what callers see. The implementation signature is checked against them only loosely: each overload must be compatible with it, and the implementation's body is checked against its own wider signature. An overload can therefore promise a return type that the implementation never produces for those arguments.

## How typerail detects it

`typerail/no-overload-signature` reports overload signatures of functions and methods that have an implementation. Ambient declarations (`declare`, `.d.ts` files) and interfaces with several call signatures are not reported; see TR209 for those.

## How to fix it

Use one signature with a union return type, or a conditional type driven by a generic parameter. When the cases differ a lot, write separate functions.
