# TR105: Shallow and aliased readonly

| | |
|---|---|
| Status | Open in TypeScript 6.0.3 |
| Checked by | Not checked yet |
| Priority | P3: latent risk |

## Example

TypeScript accepts this code under `@wingravity/typerail/tsconfig.json`:

```ts
interface Config {
  readonly options: { retries: number };
}

const config: Config = { options: { retries: 3 } };

function tune(options: { retries: number }): void {
  options.retries = -1;
}

export function proof(): unknown[] {
  tune(config.options);
  return new Array(config.options.retries);
}
```

At runtime: `RangeError: Invalid array length`

The example is [`test/gaps/TR105.ts`](../../test/gaps/TR105.ts). The test suite checks that TypeScript still accepts it and that it still fails when run.

## Why TypeScript allows it

`readonly` restricts writes through one reference. It does not freeze the value: nested objects stay writable, and any other reference to the same object, including a function parameter without `readonly`, can change it. `Readonly<T>` and `as const` are erased at compile time and do not call `Object.freeze`. TypeScript also accepts an object with `readonly` properties where a type with writable properties of the same type is expected.

## How typerail detects it

Not checked yet. TR102 covers the cases where the writable reference has a wider type. A rule for same-type writes would report a large amount of correct code, so this code documents the gap for now.

## How to fix it

Make nested types readonly too, accept `Readonly<T>` in functions that only read, and copy or freeze values at ownership boundaries.
