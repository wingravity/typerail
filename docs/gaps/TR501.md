# TR501: Unhandled promise

| | |
|---|---|
| Status | Open in TypeScript 6.0.3 |
| Checked by | `@typescript-eslint/no-floating-promises` |
| Priority | P0: process can go down; P1 in browser code |

## Example

TypeScript accepts this code under `@wingravity/typerail/tsconfig.json`:

```ts
async function save(): Promise<void> {
  await Promise.resolve();
  throw new Error("save failed");
}

export function proof(): void {
  save();
}
```

At runtime: `Error: save failed, reported as an unhandled rejection. Node stops the process.`

The example is [`test/gaps/TR501.ts`](../../test/gaps/TR501.ts). The test suite checks that TypeScript still accepts it and that it still fails when run.

## Why TypeScript allows it

A `Promise<T>` describes the value it fulfills with, not whether it rejects. TypeScript does not require a promise to be awaited or handled. Since Node 15, an unhandled rejection stops the process.

## How typerail detects it

`@typescript-eslint/no-floating-promises` reports a promise that is neither awaited, returned nor handled with `.catch` or `.then` with a rejection handler.

## Browser code

In a browser, an unhandled rejection does not stop anything: it is logged, and the failure is lost. typerail reports these findings as P1 instead of P0 in browser code, which it recognizes by:

- a tsconfig whose `lib` includes DOM and whose `types` do not include `node`, or whose `types` include `vite/client`, except Next.js configurations, which mix server and client code;
- files that start with `"use client"`.

## How to fix it

Await or return the promise. In fire-and-forget code, handle the rejection with `.catch`.
