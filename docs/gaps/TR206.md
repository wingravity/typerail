# TR206: Unchecked type predicate

| | |
|---|---|
| Status | Open in TypeScript 6.0.3 |
| Checked by | `typerail/no-type-predicate` |
| Priority | P1: silent wrong result |

## Example

TypeScript accepts this code under `typerail/tsconfig.json`:

```ts
interface User {
  id: string;
}

function isUser(value: unknown): value is User {
  return typeof value === "object" && value !== null;
}

export function proof(): string {
  const value: unknown = { id: 42 };
  return isUser(value) ? value.id.toUpperCase() : "";
}
```

At runtime: `TypeError: value.id.toUpperCase is not a function`

The example is [`test/gaps/TR206.ts`](../../test/gaps/TR206.ts). The test suite checks that TypeScript still accepts it and that it still fails when run.

## Why TypeScript allows it

TypeScript trusts a hand-written type predicate (`value is User`) or assertion function (`asserts value is User`) without comparing the claim to the function body. A predicate that checks too little narrows values that do not match the type. Since TypeScript 5.5, the compiler infers a predicate from a function body when the body proves it, and inferred predicates are checked.

## How typerail detects it

`typerail/no-type-predicate` reports explicit predicates and assertion signatures on functions and methods with a body. Inferred predicates, such as `items.filter((item) => item !== undefined)`, are not reported.

## How to fix it

Validate with a schema library. For simple cases, narrow and then build the typed value from the narrowed parts, so nothing is claimed:

```ts
if (typeof value === "object" && value !== null && "id" in value) {
  const { id } = value;
  if (typeof id === "string") {
    return { id };
  }
}
```

For filters, remove the annotation and let TypeScript infer the predicate.
