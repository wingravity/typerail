# TR209: Declaration that does not match the implementation

| | |
|---|---|
| Status | Open in TypeScript 6.0.3 |
| Checked by | Not checked yet |
| Priority | P1: silent wrong result |

## Example

TypeScript accepts this code under `@wingravity/typerail/tsconfig.json`:

```ts
import { loadUser } from "./TR209-lib.js";

export function proof(): string {
  return loadUser().name.toUpperCase();
}
```

At runtime: `TypeError: Cannot read properties of null (reading 'name')`

The example is [`test/gaps/TR209.ts`](../../test/gaps/TR209.ts). The test suite checks that TypeScript still accepts it and that it still fails when run.

## Why TypeScript allows it

Declaration files and `declare` statements describe JavaScript that the compiler never checks. Stale `@types` packages, hand-written `.d.ts` files, generated API clients and native bindings can all describe a function as returning a `User` while it returns `null`. The example's `TR209-lib.d.ts` declares `loadUser(): User`, and `TR209-lib.js` returns `null`.

## How typerail detects it

Not checked yet. A linter cannot see whether JavaScript matches its declarations. This code documents the gap.

## How to fix it

Prefer packages that ship their own types, keep `@types` packages at the same version as the runtime package, test declarations you write, and validate values that cross untrusted module boundaries.
